## Material supplementary findings (omitted from the claim narrative)

### Finding A (HIGH) — The entry cap was NOT the only guard blocking JUP; the PHANTOM-WRITE guard froze the persisted SL
From `pipeline.log`, trade 16005 SL write history:
- 14:29–14:32: trailing correctly ratcheted SL 0.359732 → 0.360220 → 0.360684 → 0.362749 → **0.36339134** (persisted, [PERSIST] lines).
- 14:33:22 → close: every tighter computation — 0.363989 (dist 0.132%), 0.364241 (dist 0.063%), 0.364470 (dist 0.000%) — was **BLOCKED by `[PHANTOM-WRITE]`** (`position_manager.py:2170-2176` in `_persist_atr_levels`: skips the DB write when new SL is <0.15% from entry).

So the persisted SL froze at -0.30% because of the phantom guard; the entry cap only additionally clamped the *computed* value. The claimed counterfactual still holds for this trade (the +0.333% lock clears the 0.15% guard), but:
- **Gap:** for peaks between ~+1.21% and ~+1.37% above entry, the fixed trailing still computes a lock that is <0.15% from entry and gets phantom-blocked — profit locking remains broken in that band.
- **Design flaw:** the guard measures distance-from-**entry**, not distance-from-**current price**, so it blocks risk-*reducing* tightenings (0.364241 was ~1% below the then-current price — zero instant-close risk — yet blocked, keeping the looser -0.30% stop that ultimately took the loss). Direction-aware check needed: block only SLs on the wrong side of current price.

### Finding B (HIGH) — Post-gate ratchet-break: above-entry profit locks are destroyed on the first sub-entry print
Running the fixed code: established LONG, lock at 0.3656835 (+0.333%), then one cycle with price below entry (tested 0.3640 and 0.3580) → the post-gate in-loss branch (`tpsl_utils.py:814-829`) rewrites SL to **entry−1.3% = 0.359732 with needs_sl=True** (line 830 flips it because post-gate new_sl differs from the original current_sl), and `_persist_atr_levels` writes it unconditionally (dist 1.3% clears the phantom guard) and pushes to HL (delta 1.63% > 0.15%). The trailing gate's one-way block is **overridden by the post-gate**.
- Root cause: the in-loss branch skips `max(new_sl, current_sl)` when `current_above_entry` (lines 817-819 + BUG-032 else-branch at 829) — written under the old invariant "SL can never be above entry"; the 2026-10-09 fix changed that invariant without updating this branch. The "stale lock" doctrine comment (2026-09-30) predates the fix.
- Impact: if the exchange-side SL order is live, price must cross the lock before reaching entry, so the stop fires first — but if the HL push failed (as in Finding A's history of blocked/failed updates), a +0.333% lock converts into a −1.3% stop (−6.5% account at 5x) — worse than the original bug.
- Fix suggestion: in the post-gate in-loss branch, apply `new_sl = max(new_sl, current_sl)` even when current_sl is above entry (an above-entry SL on a still-open trade is a live profit lock, not stale state), or gate it on `highest_price*(1-trail_dist) >= current_sl`.
- SHORT mirror (pre-existing, not introduced by this fix): verified lock at 0.3575 below entry is rewritten to entry+1.3% = 0.369208 with `_force_write=True` when price re-crosses entry.
