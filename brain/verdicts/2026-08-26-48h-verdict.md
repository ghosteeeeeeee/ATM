### 1.2 Why PM Trail Never Fires

PM Trail activates when a trade reaches 0.40% profit (PM_TRAIL_ACTIVATE_PCT = 0.004). The mechanism:

1. Trade enters at signal
2. ATR SL is set at entry ± 0.80% (ATR_SL_MIN floor)
3. Price moves against the trade
4. ATR trailing kicks in, tightening SL via `compute_atr_sl_tp()` in tpsl_utils.py
5. `check_atr_tp_sl_hits()` runs BEFORE `profit_monster.run()` in the pipeline
6. If the trailed SL is hit → trade closes via `atr_sl_hit` BEFORE PM Trail gets a chance to fire

**The ATR SL is preempting PM Trail.** The pipeline order is:
```
refresh_current_prices() → _collect_atr_updates() → _persist_atr_levels() 
→ check_atr_tp_sl_hits() → profit_monster.run()
```

ATR SL check runs first. When price drops to the trailed SL level, the trade closes immediately. PM Trail never gets its turn.

### 1.3 Why This Is Catastrophic

The 30-day data shows:
- ATR SL exits: 26.4% WR, -$27.52 (the #1 loss mechanism)
- PM Trail exits: 93.1% WR, +$20.85 (the #1 profit mechanism)

**Without PM Trail, the system bleeds.** The 48h data confirms: -$0.70 on 71 trades with 55% WR. The system needs PM Trail's 93% WR wins to offset ATR SL's losses.

## 2. THE "BLOW THROUGH SL" MYTH — DEBUNKED

### 2.1 The Leverage Illusion

The claim "avg loss 2.85% vs SL width 0.67% = trades go 4x past SL" is **wrong**. The mechanism:

| Metric | Value |
|--------|-------|
| Avg pnl_pct (leveraged) | 2.88% |
| Avg leverage | 4.28x |
| Avg raw loss (unleveraged) | 0.66% |
| SL width (sl_distance column) | 0.80% |
| **Raw loss / SL width** | **0.83x** |

**`pnl_pct` is leveraged.** Confirmed by checking individual trades:
```
BCH SHORT 5x: raw=-0.849% × 5 = -4.245% = stored pnl_pct=-4.2451% ✓
ZRO SHORT 5x: raw=-1.098% × 5 = -5.490% = stored pnl_pct=-5.4899% ✓
```

The "2.85% loss" is `0.66% raw × 4.28x leverage = 2.83%`. Trades are NOT going 4x past the SL. The raw loss is 83% of the SL width — actually LESS than the SL.

### 2.2 Exit vs SL Gap (Slippage)

For the 28 losing trades:

| Metric | Value |
|--------|-------|
| Exits within 0.1% of SL | 16 (57%) |
| Exits 0.1-0.5% past SL | 8 (29%) |
| Exits >0.5% past SL | 4 (14%) |
| Max slippage | 0.68% (JUP SHORT) |

Most trades exit very close to the SL. The 14% with >0.5% slippage are genuine execution gaps, not systemic blow-through.

### 2.3 Why SL Width Shows 0.67% Instead of 0.80%

The `sl_distance` column is **always 0.008 (0.80%)** — it's the INITIAL SL parameter, not the SL at close. The actual ABS SL width from entry at close time is 0.683%, because:

1. 53.7% of trades have SL on the WRONG side of entry (traded into profit)
2. For these trades, `abs(stop_loss - entry_price) / entry_price` is small because the SL is near entry
3. This drags down the average ABS SL width to 0.683%

The "0.67%" is an artifact of trailing — the SL moves during the trade, so measuring it at close gives a different number than at entry.

## 3. THE MECHANISM: WHY AVG LOSS DIFFERS FROM SL WIDTH

### 3.1 For LOSERS (28 trades)

| Metric | Value |
|--------|-------|
| Avg raw loss | 0.86% |
| SL width at close | 0.80% (sl_distance) |
| Actual SL from entry | 0.80% (correct side) |
| Ratio | 1.08x |

**Losers are stopped at the SL with ~0.06% slippage.** The 8% excess is normal execution variance on HyperLiquid.

### 3.2 For WINNERS (39 trades closed via atr_sl_hit)

| Metric | Value |
|--------|-------|
| Avg raw profit | 0.52% |
| SL position | Wrong side of entry (above for LONG) |
| MFE | 1.09% |
| MAE | 0.29% |

**Winners have SL trailed into profit territory.** The ATR trailing moved the SL above entry (for LONG) or below entry (for SHORT), then when price reversed, it hit the trailed SL — but the trade was still in profit.

These trades closed via `atr_sl_hit` because the ATR SL check runs before PM Trail in the pipeline. The trade reached profit, the SL trailed up, price reversed, and the ATR SL fired — closing at a small profit instead of letting PM Trail capture more.

### 3.3 The Root Cause: Pipeline Order Conflict

```
Pipeline execution order:
1. refresh_current_prices()     — updates current_price from HL
2. _collect_atr_updates()       — computes new SL/TP via tpsl_utils
3. _persist_atr_levels()        — writes SL/TP to DB
4. check_atr_tp_sl_hits()       — checks if SL/TP hit → CLOSES TRADE
5. profit_monster.run()         — checks for PM Trail exits → TOO LATE
```

Step 4 fires BEFORE step 5. When the ATR SL is trailed to a level that current_price has crossed, the trade closes immediately. PM Trail never gets its turn.

**This is a pipeline ordering bug.** PM Trail should run BEFORE ATR SL check, or they should run simultaneously with a priority system.

## 4. WHAT-IF SIMULATIONS

### 4.1 Hard SL at Different Levels (48h data)

| Hard SL | Trades | WR | Total PnL | Avg PnL |
|---------|--------|-----|-----------|---------|
| 0.5% | 70 | 45.7% | -$6.52 | -$0.093 |
| 0.6% | 70 | 48.6% | -$7.20 | -$0.103 |
| 0.7% | 70 | 51.4% | -$7.82 | -$0.112 |
| 0.8% (current) | 70 | 55.7% | -$7.80 | -$0.112 |
| **1.0%** | **70** | **55.7%** | **-$1.74** | **-$0.025** |
| **1.2%** | **70** | **55.7%** | **-$1.02** | **-$0.015** |
| 1.5% | 70 | 55.7% | -$0.51 | -$0.007 |
| 2.0% | 70 | 55.7% | -$0.51 | -$0.007 |

**Counterintuitive finding: WIDER SL produces BETTER results in this 48h period.**

Why? Because the simulation uses MAE (maximum adverse excursion) to determine if a trade would have been stopped. Trades with MAE > hard_sl are assumed stopped at hard_sl. Trades with MAE < hard_sl keep their actual outcome.

With tighter SL (0.5-0.8%):
- More trades get stopped (55-70% hit SL)
- These trades are stopped at a loss
- Many would have recovered if given more room

With wider SL (1.0-1.5%):
- Fewer trades get stopped (only those with MAE > 1.0%)
- Trades that would have been stopped at 0.8% recover and become winners
- The wins from recovered trades outweigh additional losses

**However:** This simulation assumes the trade outcome is fixed (the actual exit). In reality, wider SL means different trade management — the simulation is a simplification.

### 4.2 The Real Problem: PM Trail Absence

The simulation doesn't account for PM Trail because PM Trail never fired in 48h. If PM Trail were active:
- Trades reaching 0.40% profit would close via PM Trail at 93% WR
- Only trades that never reach 0.40% profit would close via ATR SL
- The system would be significantly more profitable

**The #1 priority is NOT changing SL width — it's restoring PM Trail functionality.**

## 5. CLAIM-BY-CLAIM VERDICT

### Claim 1: "SL width dropped from 1.00% to 0.67% — the 0.8% floor is working"
**PARTIAL — direction correct, numbers misleading**

The `sl_distance` column is 0.80% (fixed). The actual ABS SL width from entry is 0.683%, but this is an artifact of trailing — 53.7% of trades have SL on the wrong side of entry. The "0.67%" is not evidence that the 0.8% floor is "working" — it's evidence that the ATR trailing is moving the SL during the trade.

### Claim 2: "Avg loss 2.85% despite SL width 0.67% means trades blow through SL"
**DISAGREE — the comparison is apples-to-oranges**

The 2.85% is leveraged (0.66% raw × 4.28x leverage). The raw loss is 0.66% vs SL width 0.80% = ratio 0.83x. Trades are NOT blowing through SL. The "3.56x blow-through" was computed by comparing leveraged pnl_pct to raw sl_distance — a meaningless comparison.

### Claim 3: "PM Trail has 0 exits — profit monster isn't catching any winners"
**AGREE — THIS IS THE CRITICAL FINDING**

Zero PM Trail exits in 48h. The profit engine is completely offline. The ATR SL check runs before PM Trail in the pipeline, preempting all PM Trail exits. This is a pipeline ordering issue, not a parameter tuning issue.

### Claim 4: "0.75% hard SL would be optimal (+54.34% cumulative)"
**DISAGREE**

My simulation shows wider SL (1.0-1.5%) is better for this 48h period. The claim of "+54.34% cumulative" is not reproducible. The real issue is not SL width — it's the absence of PM Trail.

### Claim 5: "The SL is being tightened DURING the trade, but damage is done before it tightens"
**PARTIAL — mechanism misunderstood**

The SL IS being tightened via ATR trailing. But it's not "damage before tightening" — the ATR SL trails INTO profit territory and closes winners at smaller profits than PM Trail would. The issue is that ATR SL fires before PM Trail, capturing less profit.

## 6. ROOT CAUSE ANALYSIS

### 6.1 ROOT CAUSE: `profit_monster.py` Deleted, Systemd Timer Not Disabled

The profit_monster.py script was deleted on 2026-08-27 (commit a6e75fb8) as part of "Guitar Tuning Phase 0." The systemd timer was never disabled. The service fails every minute with exit code 2.

**This is the #1 issue.** Without profit_monster, there is no PM Trail, no Tier 1/2 profit-taking, and no cut_loser trail. All profit-taking and loss-cutting that was handled by profit_monster is gone.

### 6.2 Secondary Issue: ATR SL Preempts What Would Be PM Trail

Even if profit_monster.py were restored, there's a pipeline ordering issue:
- `check_atr_tp_sl_hits()` runs BEFORE `profit_monster.run()` in the position_manager loop
- When ATR SL is trailed to a level that price has crossed, the trade closes immediately
- PM Trail never gets its turn

**Fix:** Either reorder the pipeline so profit_monster runs first, or skip ATR SL check for trades in profit that haven't reached PM Trail activation threshold.

### 6.3 Why the 48h Period Is Different

The 30-day baseline has 32.7% PM Trail exits. The 48h period has 0%. This is because:
1. **profit_monster.py was deleted** — the script literally doesn't exist
2. **Systemd timer keeps firing** — but the service fails every time
3. **All trades close via ATR SL** — because there's no other exit mechanism running

### 6.4 The ATR SL Trailing Tightness

The ATR trailing in `tpsl_utils.compute_atr_sl_tp()` uses `ATR_SL_MIN_ACCEL = 0.30%` for established trades in profit. This means the SL is only 0.30% from the peak. Normal market noise (>0.30%) triggers the SL before the trade can develop.

**But this is secondary to the profit_monster deletion.** Even with tight ATR SL, profit_monster should be catching trades that reach 0.40% profit before ATR SL fires.
