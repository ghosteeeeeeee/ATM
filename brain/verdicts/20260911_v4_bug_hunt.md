## CRITICAL

### ISSUE 1: Confidence 90-94 Block Is Dead Code (Never Triggers)
**SEVERITY:** CRITICAL  
**FILE:** `/root/.hermes/scripts/signals/accel_300_v4_short.py:440-441`  
**DETAIL:** The V4 "confidence 90-94 block (33% WR trap)" can never fire. Confidence is capped at 88 by TWO independent ceilings before the check:
1. `ACCEL_300_V4_SHORT_CONF_CAP = 88` (hermes_constants.py:1967) → line 435-436 caps `confidence` at 88
2. `add_signal()` in signal_schema.py:695-697 has `MAX_CONFIDENCE = 88` (defense-in-depth)

The block check `ACCEL_300_V4_SHORT_CONF_BLOCK_MIN(90) <= confidence <= ACCEL_300_V4_SHORT_CONF_BLOCK_MAX(94)` is unreachable because `confidence ≤ 88 < 90`. The V4 docstring claims this was a key addition ("V4 ADDITIONS: 10. Confidence 90-94 block"), but it's completely inoperative.

**FIX:** Either:
- (a) Change `ACCEL_300_V4_SHORT_CONF_CAP` to 95 and let `add_signal()` handle the final cap, OR
- (b) Lower the block range to match achievable confidence values (e.g., CONF_BLOCK_MIN=82, CONF_BLOCK_MAX=88), OR
- (c) Remove the dead constants/check and update the docstring to reflect reality

## HIGH

### ISSUE 2: V4 Reuses V3 Execution Constant (Cross-Signal Fragility)
**SEVERITY:** HIGH  
**FILE:** `/root/.hermes/scripts/decider_run.py:3485`  
**DETAIL:** V4 execution-time price-move check reuses `ACCEL_300_V3_SHORT_MAX_ENTRY_MOVE`:
```python
from hermes_constants import ACCEL_300_V3_SHORT_MAX_ENTRY_MOVE  # reuse V3 constant
```
If this constant is tuned for V3 (which has different entry conditions — RSI filter, z-score filter), V4 silently inherits the wrong threshold. V4 has a wider gap range (2-6%) and different momentum profile than V3 — a single entry-move constant may not be appropriate for both.

**FIX:** Add a dedicated `ACCEL_300_V4_SHORT_MAX_ENTRY_MOVE` constant in hermes_constants.py and use it in decider_run.py.

### ISSUE 3: Null Price Crash in Detection Function
**SEVERITY:** HIGH  
**FILE:** `/root/.hermes/scripts/signals/accel_300_v4_short.py:207`  
**DETAIL:** `_get_1m_prices()` does not filter NULL prices from `price_history`:
```python
# Line 148 — no NULL filter
return [{'timestamp': r[0], 'price': r[1]} for r in rows]
```
Then `detect_accel_300_v4_short()` does:
```python
closes = [float(p['price']) for p in prices]  # line 207
```
If any price is NULL (None in Python), `float(None)` raises `TypeError`, crashing the entire detection for that token. While rare, corrupted price data has occurred in this system (see AGENTS.md: "data corruption fix").

**FIX:** Filter NULL prices in `_get_1m_prices`:
```python
return [{'timestamp': r[0], 'price': r[1]} for r in rows if r[1] is not None]
```

## MEDIUM

### ISSUE 4: Dead FLAT Regime Check in Signal File
**SEVERITY:** MEDIUM  
**FILE:** `/root/.hermes/scripts/signals/accel_300_v4_short.py:419-427`  
**DETAIL:** The explicit FLAT regime block on lines 426-427 is unreachable:
```python
trade_ok, regime = should_trade(token, signal=SOURCE)
if not trade_ok:
    continue       # ← catches FLAT here (V4 not in FLAT's REGIME_SIGNALS)
if regime == 'FLAT':
    continue       # ← DEAD CODE: unreachable when should_trade works
```
Since `accel-300-v4-short-` is NOT in `volatility_gate.REGIME_SIGNALS['FLAT']`, `should_trade()` returns `('SKIP', ...)` when regime is FLAT. The `if not trade_ok: continue` catches it first. After an exception, `regime` isn't defined so the check is also unreachable.

The check is harmless but misleading — it suggests the FLAT block is a separate mechanism when it's actually handled by `should_trade()`.

**FIX:** Remove lines 426-427 or add a comment: `# Note: FLAT is already blocked by should_trade() above — this is defense-in-depth for should_trade exceptions`.

### ISSUE 5: Fragile Import of `fast_momentum` (Not Wrapped in try/except)
**SEVERITY:** MEDIUM  
**FILE:** `/root/.hermes/scripts/signals/accel_300_v4_short.py:346`  
**DETAIL:** Inside `scan_accel_300_v4_short_signals()`:
```python
from signals.fast_momentum import recent_trade_exists, MIN_TRADE_INTERVAL_MINUTES
```
This is NOT wrapped in try/except. If `fast_momentum.py` is ever removed or renamed (as many legacy signals have been), this import crashes the entire V4 scanner, silently preventing all V4 signals from firing. Other signals wrap similar imports in try/except or use lazy imports.

**FIX:** Wrap in try/except with a fail-open fallback:
```python
try:
    from signals.fast_momentum import recent_trade_exists, MIN_TRADE_INTERVAL_MINUTES
except ImportError:
    recent_trade_exists = lambda *a: False
    MIN_TRADE_INTERVAL_MINUTES = 5
```

### ISSUE 6: Phase Filter Always Disabled (Dead Code)
**SEVERITY:** MEDIUM  
**FILE:** `/root/.hermes/scripts/signals/accel_300_v4_short.py:408-417`  
**DETAIL:** `PHASE_ENTRY_FILTER_ENABLED = False` (hermes_constants.py:742), so the entire phase filter block:

if PHASE_ENTRY_FILTER_ENABLED:
    from tpsl_utils import _get_current_phase
    phase = _get_current_phase(token)

**FIX:** Either remove the dead code or fix the typo (`'trendin'` → `'trending'`).

### ISSUE 7: V4 Not in FLAT Regime Set — But Is This Sufficient?
**SEVERITY:** MEDIUM  
**FILE:** `/root/.hermes/scripts/volatility_gate.py:32-55`  
**DETAIL:** `accel-300-v4-short-` is correctly absent from `REGIME_SIGNALS['FLAT']` but is present in NORMAL (line 77), HIGH (line 122), and EXTREME (line 177). The V4 docstring says "FLAT: 0 trades (V2 naturally avoided, but V4 blocks explicitly)."

However, the `should_trade()` function's EXTREME behavior is regime-gated differently:
```python
elif regime == 'EXTREME':
    return ('SKIP', f'storm: ATR={atr_pct:.4f}% > 1.5% (signal not suited)')
```
For EXTREME with a signal provided, if the signal IS in the EXTREME set, it returns `('TRADE', 'EXTREME')`. V4 is in the EXTREME set, so it CAN fire in EXTREME. This matches the regime performance data ("EXTREME: 52% WR, +$0.36"). However, there's no V4-specific EXTREME guard — the V2 data showed EXTREME at 52% WR which is the weakest winning regime. A future enhancement could block EXTREME for V4.

**FIX:** No action needed now — this is a tuning consideration for later.

## LOW

### ISSUE 8: Dual Cooldown Mechanism (Complexity)
**SEVERITY:** LOW  
**FILE:** `/root/.hermes/scripts/signals/accel_300_v4_short.py:374-397, 479`  
**DETAIL:** V4 uses TWO independent cooldown systems:
1. **Direct SQLite query** (lines 374-397): Queries `signals` table for last signal with same source, blocks if < 15 min elapsed
2. **`set_cooldown()`** (line 479): Writes to `loss_cooldowns.json` with 15-minute expiry

These serve different purposes (pre-signal vs post-signal), but the redundancy adds complexity. If one system fails, the other still works. This is defense-in-depth, not a bug.

**FIX:** No action needed.

### ISSUE 9: Volume Filter Threshold (MULT=1.0 = Average)
**SEVERITY:** LOW  
**FILE:** `/root/.hermes/scripts/signals/accel_300_v4_short.py:184`  
**DETAIL:** `ACCEL_300_V4_SHORT_VOLUME_MULT = 1.0` means the latest bar's volume must be >= average volume. With this threshold, roughly 50% of signals are blocked based on whether the latest bar happened to have above-average volume. This is a valid filter but the `VOLUME_MULT` constant name suggests it should be a multiplier, and 1.0 is the boundary value.

**FIX:** No action needed — this is a tuning parameter. Consider 0.8 if 50% rejection is too aggressive.

### ISSUE 10: `add_signal` MAX_CONFIDENCE Caps V4 Before Compactor
**SEVERITY:** LOW  
**FILE:** `/root/.hermes/scripts/signal_schema.py:695-697`  
**DETAIL:** `add_signal()` has `MAX_CONFIDENCE = 88` which caps ALL signals, not just V4. V4's `CONF_CAP = 88` matches, so there's no discrepancy. But if someone changes V4's CONF_CAP to, say, 90, `add_signal` would silently clamp it back to 88. Double-capping is redundant but harmless.

**FIX:** No action needed — defense-in-depth.

## UNCERTAINTIES

1. **`add_signal` merge behavior**: If V4 fires for a token+direction that already has a pending signal from another signal_type, `add_signal` merges them into one row. The merged row's `signal_type` might not be `'accel_300_v4_short'`, which could affect the compactor's source weight lookup. I did not fully trace the merge logic — it may work correctly via the `source` field matching, but this warrants verification with a test case.

2. **`recent_trade_exists` from `fast_momentum`**: I assumed this function exists and works correctly. If it has bugs (e.g., wrong time window, stale data), V4 signals could be incorrectly blocked or allowed. I did not audit `fast_momentum.py`.

3. **`_get_1m_prices` returning data from STATIC_DB vs CANDLES_DB**: V4's `_get_1m_prices` reads from `STATIC_DB` (price_history table), while `_check_volume` reads from `CANDLES_DB` (candles_1m table). These are different databases with different update cadences. A race condition where price_history is updated but candles_1m is not (or vice versa) could cause inconsistent signal detection. This is a pre-existing architectural issue, not V4-specific.

4. **Confidence block at 88 by `add_signal`**: I'm confident this is a real bug (Issue 1) but acknowledge it's possible the intent was for the CONF_BLOCK to be a future-looking constant that would take effect if CONF_CAP is ever raised. However, the docstring says it's a current V4 addition, so I treat it as a bug.
