## BUGS FOUND

### 1. MINOR: signal_outcomes.created_at is NOT detection time
**Severity: LOW**
The `created_at` column uses `DEFAULT CURRENT_TIMESTAMP` at INSERT time. The INSERT happens when the trade CLOSES (in `record_signal_outcome()`), not when the signal is DETECTED. This means `created_at` is the trade close time, not the detection time.

The context provided claimed "created_at and closed_at are BOTH signal detection timestamps" — this is incorrect based on the code. Both are set to the current time when the INSERT executes at trade close.

**Impact:** Any analysis using `created_at` as "detection time" will have timing errors. For fast trades (close within minutes), the error is small. For slow trades, it could be significant.

### 2. CONFIDENCE OVERFLOW: ETC trade has confidence=102
**Severity: LOW**
The detection function caps confidence at MAX_CONFIDENCE=88. The ETC trade has confidence=102, which means the confidence was boosted by the signal_compactor (compound signal scoring). This is working as designed — the compactor can boost confidence beyond the detection function's cap.

### 3. NO BUGS in detection or re-validator logic
The detection function correctly implements all 7 conditions with proper early returns. The re-validator correctly implements the 3 stable conditions. Both use identical EMA computation. No logic errors found.

## FINAL ASSESSMENT

### Overall Quality of the Changes: GOOD

**Strengths:**
1. Data-driven design: 7 conditions derived from analysis of 16 historical trades
2. The analysis correctly identified the key differentiator: slope direction (positive = loss, negative = win)
3. The re-validator uses identical computation to the detection function (verified)
4. C7 (consec≥20) provides defense-in-depth without being overly restrictive
5. The slope threshold of 0.0 is correct (verified: -0.1 blocks 4/7 winners)
6. The signal is appropriately conservative

**Weaknesses:**
1. **The redesign hasn't been tested in production.** It was committed AFTER all 16 trades. No live trades have used the new 7-condition code yet.
2. **The original 6-condition code had 33% WR (9L/7W).** The redesign is expected to improve this, but it's unproven.
3. **The re-validator was never actually deployed for these trades.** The claim that it "blocks 9/9 losses" is hypothetical.
4. **The `signal_outcomes.created_at` is not the detection timestamp.** This could cause confusion in future analyses.

**Recommendation:**
- Keep the signal enabled as-is (7 conditions + 3-condition re-validator)
- Monitor for at least 20+ trades before drawing conclusions about the redesign's effectiveness
- Fix the `signal_outcomes.created_at` to record detection time, not close time
- Consider adding detection-time metadata to signal_outcomes for future audits
