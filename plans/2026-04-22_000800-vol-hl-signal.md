# Plan: Volume Alert → Hyperliquid Signal (Local Candle Data)

## Goal
Monitor HL's own 1m candle data (already stored locally in `candles.db`) and emit signals when a coin's volume exceeds N× its 10-period SMA. Feed those signals through the existing Hermes pipeline → guardian → HL execution.

---

## Data Flow

```
candles.db (local HL 1m candles)
       ↓
volume_hl_signals.py  (new standalone script)
       ↓
add_signal()  →  signals_hermes_runtime.db
       ↓
signal_compactor.py  (runs every 1 min via hermes-pipeline.timer)
       ↓
hotset.json  (/var/www/hermes/data/hotset.json)
       ↓
hl-sync-guardian.py  (reads hotset, executes on Hyperliquid)
```

---

## Step-by-Step Plan

### Step 1: Create `volume_hl_signals.py`

**Location:** `/root/.hermes/scripts/volume_hl_signals.py`

**Logic per token:**
1. Query `candles_1m` for last 11 candles from `candles.db`
2. Compute 10-period SMA of volume from candles[0:10]
3. Current volume = candles[10]["volume"]
4. Ratio = current_vol / sma_vol
5. If ratio >= VOL_MULT and current_vol >= MIN_VOL:
   - Direction: `LONG` if price_up, `SHORT` if price_down (price change over the 10m window)
   - Confidence = `min(88, ratio * 10)` — capped at 88 to match existing signal ceiling
   - Call `add_signal()` with source=`volume_binance` (or `volume_hl`)

**Config at top:**
```python
SCAN_SECS    = 60        # match pipeline cadence
VOL_MULT     = 5.0        # fire at N× SMA
MIN_VOL      = 10_000     # minimum volume (USD, quote volume) to qualify
TIMEFRAME    = "1m"
HL_EXCHANGE  = "hyperliquid"
MIN_CONFIDENCE = 50      # floor — HL requires ≥50
```

**DB path:** `/root/.hermes/data/candles.db` (table: `candles_1m`)

**Schema for candles_1m:**
```sql
token TEXT, ts INTEGER, open REAL, high REAL, low REAL, close REAL, volume REAL
PRIMARY KEY (token, ts)
```

### Step 2: Map symbol (HL coin name → our token name)

HL uses coin names like `BTC`, `ETH`, `1000SHIB`. The `candles.db` stores `token` column using these same names. We need to get the list of active tokens — can query distinct tokens from `candles_1m`.

### Step 3: How to get token list

```python
c.execute("SELECT DISTINCT token FROM candles_1m ORDER BY token")
tokens = [row[0] for row in c.fetchall()]
```

### Step 4: Call add_signal()

```python
from signal_schema import add_signal

# after computing ratio, direction, confidence:
add_signal(
    token=token,
    direction=direction,          # 'LONG' or 'SHORT'
    signal_type='volume_hl',
    source='volume_hl',            # used for blacklist checks
    confidence=confidence,
    value=ratio,
    price=current_close,
    exchange=HL_EXCHANGE,
    timeframe=TIMEFRAME,
    z_score=None,
    z_score_tier=None,
)
```

### Step 5: Run on Tokyo server via systemd

Systemd unit so it auto-restarts on crash and starts on boot.

### Step 6: Validate

1. Run manually: `python3 volume_hl_signals.py`
2. Check `signals_hermes_runtime.db`: `SELECT token, direction, confidence, source FROM signals WHERE source='volume_hl' ORDER BY created_at DESC LIMIT 10;`
3. After next pipeline run: check `hotset.json` for volume_hl entries
4. Confirm guardian picks them up and executes on HL

## Key Constraints

- `add_signal()` requires confidence >= 50, caps at 88
- Token names in `candles.db` must match HL coin names exactly
- Guardian executes on Hyperliquid only — no Binance needed (we use HL's own candle data)
- Must run on Tokyo server (has access to `candles.db` which is on this machine)

---

## Risks

- If `candles.db` is stale/empty for a token → skip silently (no crash)
- If many coins pump at once → many signals → hot-set flooded → guardian may execute many
  - Consider: if alert_count > 10 in one cycle, log warning and optionally skip lowest-confidence ones
- Some HL tokens might not be in `candles_1m` yet (new listings) — handled gracefully by skipping
