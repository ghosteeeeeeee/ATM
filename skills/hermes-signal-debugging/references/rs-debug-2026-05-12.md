# RS Signal Debug Reference

## Bug: add_signal() missing required args (2026-05-12)

**Symptom:** RS signals completely silent for ~21 days. No RS entries in hot-set, pipeline log showed `[rs] STALE` for all tokens (wrong staleness diagnosis).

**Root Cause:** `signals/rs.py` line 667 — `scan_rs_signals()` called `add_signal()` without `source` and `confidence`:
```python
# BROKEN — TypeError on every token, scan silently crashes
sid = add_signal(
    token=token.upper(),
    direction=sig['direction'],
    signal_type=RS_SIGNAL_TYPE,
)

# FIXED
sid = add_signal(
    token=token.upper(),
    direction=sig['direction'],
    signal_type=RS_SIGNAL_TYPE,
    source=sig['source'],        # ADDED
    confidence=sig['confidence'],  # ADDED
)
```

**Diagnosis path:**
1. Log showed `[rs] STALE` for ts=1778568322 but DB max_ts was only ~120s old → staleness check logic sound, wrong diagnosis
2. Confirmed DB freshness: `SELECT MAX(timestamp) FROM price_history` for all tokens — all FRESH (<120s)
3. Ran `scan_rs_signals()` directly → saw TypeError in traceback, identified missing two required positional args
4. `add_signal()` signature: `add_signal(token, direction, signal_type, source, confidence, ...)`

**After fix:** RS scan fires 56+ signals per run, writing to `signals_hermes_runtime.db` correctly.

## Staleness check mechanics (for future debugging)

The RS staleness check uses `rows[-1][0]` after an ASC sort of a DESC subquery. This is CORRECT — `rows[-1]` is the newest timestamp in the returned window, not the oldest.

```python
# Query: ORDER BY timestamp DESC LIMIT 4700 → outer ORDER BY timestamp ASC
# Result: rows[0] = oldest, rows[-1] = newest (freshest in window)
most_recent_ts = rows[-1][0]  # CORRECT — newest
if (time.time() - most_recent_ts) > 120:
    return []  # skip stale
```
